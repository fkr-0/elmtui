** 3. State Management & Elm Integration
   - [x] Integrate transactional, observable, thread-safe state (statelib) as core API.
     - Core `application-state` struct manages data, lock, transaction logs, and observers.
     - Thread-safety provided via mutex (`application-state-lock`).
     - Transactionality provided via `with-transaction` macro.
     - Basic observer mechanism implemented (`add/remove/notify-observers`).
   - [x] Rewire defmodel macro:
     - [x] Generate schema/slot definitions for application-state hash-table.
       - Models are defined as schemas, instances are stored as plists in the central `application-state` hash-table, keyed by the model name symbol.
     - [x] Provide contract-based slot validation and defaulting.
       - `:type`, `:initform`, and `:validate` options implemented in the generated `make-<model-name>` constructor.
     - [x] Optionally auto-generate observer hooks for model fields.
       - `:observe t` flag in slot definition triggers registration via `ut.state:add-observer` in the `initialize-<model-name>-state` helper function.
       - Observers watch the top-level model plist; the callback filters for changes to the specific slot.
     - [x] Document idiomatic usage with application-state.
       - Docstrings updated to reflect schema-based approach, plist storage, accessors, and mandatory use of `defupdate` for modifications.
   - [x] Rewire defmsg macro:
     - [x] Register allowed message variants for runtime validation.
       - Variants registered in `*message-schemas*`.
       - `make-<variant>-<type>` constructor functions generated for each variant, performing basic type checks on arguments. Recommended usage.
       - `message-variant-p` provides basic keyword validation.
     - [ ] Integrate with observer/dispatcher for fine-grained subscriptions.
       - Placeholder comments added; requires further integration, potentially with `clevelib.ems`.
     - [x] Document message variant usage and anti-patterns.
       - Docstrings updated, emphasizing use of generated constructors.
   - [x] Rewire defupdate macro:
     - [x] Ensure all updates are performed transactionally on application-state.
       - Body wrapped in `ut.state:with-transaction`.
       - Mandatory local `set-state!` macro ensures changes call `ut.state:record-change`.
     - [PARTIAL] Provide macroexpansion-time error reporting for side-effects.
       - Basic heuristic warning implemented for direct use of `setf`, `setq`, etc. Not full static analysis.
     - [x] Support undo/redo and time-travel via transaction history.
       - Implemented in `statelib` via `undo-last-transaction`, `redo-last-transaction`, using `transaction-history` and `undone-history` lists.
     - [x] Document update patterns for idiomatic Elm-style workflows.
       - Docstrings updated to explain transactional updates via `set-state!`.
   - [PARTIAL] Provide usage patterns and documentation for new state workflow.
     - Docstrings in macros updated. Requires consolidated usage guide.
     - *** New State Workflow Summary: ***
       1. Define models using `defmodel` (specifies schema, generates constructor/accessors).
       2. Define messages using `defmsg` (specifies variants, generates constructors).
       3. Initialize `application-state` (using `ut.state:make-application-state`).
       4. Create initial model state plists using `make-<model-name>`.
       5. Add initial state to app-state and register observers using `initialize-<model-name>-state`.
       6. Define update logic using `defupdate`, modifying state *only* via the local `set-state!` macro.
       7. Create messages using `make-<variant>-<type>` constructors.
       8. Dispatch messages to the appropriate `defupdate`-defined function.
       9. Access state using `state-ref` or generated model accessors (`<slot-name>`).
       10. Use `ut.state:undo-last-transaction` / `ut.state:redo-last-transaction` for history navigation.
   - [ ] Add tests for transactional updates, observer notifications, and undo/redo.
     - Formal test suite still required.
