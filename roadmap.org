* ElmTUI: Professional Implementation Roadmap & Architecture

** Introduction & Current Status

This document outlines the roadmap for developing ElmTUI into a professional, robust, and idiomatic Common Lisp TUI framework inspired by The Elm Architecture (TEA).

Recent development efforts focused on resolving a significant number of compilation warnings and dependency issues across various modules (core, state, platform, UI, styling). This involved:
- Correcting package definitions and load order in =elmtui.asd=.
- Resolving circular dependencies (e.g., by introducing =src/core/globals.lisp=).
- Fixing undefined function/variable/type errors through corrected imports, exports, function names, and adding missing definitions.
- Refining macro expansions (=defstylegroup=, =with-async-restarts=).
- Ensuring class definitions are available at compile-time where needed (=eval-when=).

Critically, to resolve immediate compilation errors stemming from legacy code in =src/ui/primitives.lisp= and =src/ui/composite.lisp=, the =elm-widget= base class and its accessors (=widget-id=, =widget-props=, etc.) were temporarily reintroduced in =src/ui/base.lisp=. *This is explicitly a short-term measure to enable compilation and further development.* It does *not* represent the target architecture for UI components, which is intended to be purely Elm-idiomatic.

** Architectural Direction: Elm-Idiomatic UI Components

The core design philosophy of ElmTUI is adherence to The Elm Architecture (TEA) for managing UI state and logic. This provides significant benefits in terms of predictability, testability, maintainability, and alignment with modern UI/UX principles.

*** TEA Principles for ElmTUI Components:
Each logical UI element (widget) should ideally be implemented as a self-contained functional unit, typically within its own package (e.g., =elmtui.ui.widgets.button=), comprising:
  - *Model*: A data structure (struct or plist) holding the component's specific state. This state is typically nested within the global =application-state=.
  - *Msg*: A set of message types the component understands or produces. Messages represent events or requests for state change.
  - *init*: A function returning the component's initial model state and optional initial commands (=Cmd=).
  - *update*: A *pure function* with the signature =(Msg, Model) -> (values Model Cmd)=. It takes a message and the current model state, returning the *new* model state and any side-effect commands (e.g., sending messages, async tasks). Crucially, it does *not* modify the state directly.
  - *view*: A *pure function* with the signature =(Model, DispatchFn) -> UI-Node=. It takes the current model state and a dispatch function (for creating event handlers), returning a declarative description of the UI subtree for that component using =ui-node= structures.

*** Contrast with Class-Based UI:
The temporarily reintroduced =elm-widget= class represents a more traditional object-oriented approach. While useful in some contexts, it deviates from the Elm ideal for UI components because:
  - It encourages encapsulating state *within* the widget object itself, rather than managing it centrally.
  - It relies on methods (=widget-update=, =widget-render=) operating on the object, rather than pure functions operating on immutable data.
  - This can lead to less predictable state flow and make debugging more complex compared to TEA's unidirectional data flow.

*** Elm-Style Composition:
Component composition in ElmTUI should follow the TEA pattern:
  - *State Nesting*: Parent components include child component models within their own model structure (e.g., a =form-model= might contain slots for a =button-model= and an =input-model=).
  - *Message Wrapping*: Parent components define messages that wrap child messages (e.g., =(:form-msg (:button-msg :click))=). The parent =update= function unwraps these messages and delegates them to the appropriate child =update= function, integrating the returned child model and commands.
  - *View Composition*: Parent =view= functions call child =view= functions, passing the relevant part of the model and a wrapped dispatch function.

** Proposed Ideal Implementation (Senior CL Perspective)

Leveraging Common Lisp's strengths to achieve an idiomatic and professional Elm-style framework:

  - *Modularity*: Strict package separation per component/subsystem (e.g., =elmtui.ui.widgets.button=, =elmtui.style-lib.core=) using =uiop:define-package= with explicit imports/exports.
  - *Centralized, Transactional State*: Utilize the =elmtui.state= system built upon =statelib=. All application state resides in a single, observable, thread-safe =application-state= instance. Component state is part of this tree.
  - *Declarative Views*: Employ the =ui-node= data structure and associated DSL macros (=container=, =text=, etc. in =elmtui.view.core=) for view functions. Views are pure data descriptions, decoupled from rendering logic.
  - *Pure Updates & Side Effects*: Enforce update purity via the =defupdate= macro, which provides transactional guarantees and the local =set-state!= macro for state modification. All side effects (async tasks, message dispatch) are handled declaratively via =Cmd= objects returned from =update= functions and interpreted by the runtime (=elmtui.core.async=, =elmtui.core.loop=).
  - *Idiomatic Common Lisp*:
    - *Macros*: Leverage macros extensively for declarative APIs (=defmodel=, =defmsg=, =defupdate=, =defview=, view DSL, styling DSL) to reduce boilerplate and enhance expressiveness.
    - *CLOS*: Use CLOS strategically for core abstractions where polymorphism and extensibility are key (e.g., platform backends via =elmtui.platform.api=, the =stylable= interface, potentially rendering dispatch) but *avoid* using =defclass= for individual UI component logic, preferring the functional TEA pattern.
    - *Condition System*: Employ the condition system robustly for error handling, signaling, and recovery (e.g., =elmtui.core.conditions= providing restarts for message validation, async tasks).
  - *UX/UI Design Alignment*: TEA's unidirectional data flow and predictable state updates simplify reasoning about UI behavior, facilitate debugging ("time travel debugging" via transaction history), and align well with modern state management patterns favored in professional UI/UX development.
