# Elmtui State Management Guide

This guide explains the idiomatic workflow for managing application state in Elmtui, leveraging the `statelib` library and the `defmodel`, `defmsg`, and `defupdate` macros. This approach follows the principles of the Elm Architecture, emphasizing unidirectional data flow, immutable state updates within transactions, and clear separation of concerns.

## Core Concepts

*   **Application State (`application-state`):** A central, thread-safe container holding the entire application's state. Internally, it uses a hash table where keys are typically model name symbols (defined via `defmodel`) or other global keys (like `:current-stylesheet`, `:global-keymap`, `:current-focus-id`, `:focusable-elements`) and values represent the state.
    *   `:current-focus-id`: Stores the ID of the currently focused widget (or `nil`).
    *   `:focusable-elements`: Stores an ordered list of IDs of widgets currently eligible to receive focus. This list is typically regenerated after each view rendering and an `:update-focusable-ids` message is dispatched.
*   **Models (`defmodel`):** Define the *schema* for structured parts of the application state (like individual components or data structures). `defmodel` generates helper functions (constructors, accessors) but does *not* create classes or structs directly representing the model instance. Model instances are simple plists stored in the `application-state`.
*   **Messages (`defmsg`):** Define the types of events or actions that can occur in the application, including UI events (key presses, clicks), focus changes (`:request-focus`, `:focus-next`, `:focus-previous`), theme changes, state changes from observers, internal updates (`:update-focusable-ids`), etc. `defmsg` generates constructors to create message data lists in a standardized format. Actual messages passed through the system are typically `clevelib.message:message` objects containing these data lists.
*   **Updates (`defupdate`):** Define pure functions that take the current application state and a message, and return the *new* application state (or rather, describe the changes) and any commands (side effects) to be executed. All state modifications within `defupdate` *must* use the local `set-state!` macro, which ensures changes are recorded transactionally.
*   **Transactions (`statelib`):** All state changes made via `set-state!` within a `defupdate` are wrapped in a transaction. This enables features like undo/redo and ensures atomicity.
*   **Observers (`statelib` + `defmodel`):** Allow reacting to specific state changes by dispatching messages back into the update loop, maintaining unidirectional flow.

## Workflow Summary

Here's a step-by-step guide to the typical workflow:

**1. Define Models (`defmodel`)**

Specify the structure of your state using `defmodel`.

```lisp
;; --- Simple Models ---
;; Define the schema for a counter model
(defmodel counter (:docstring "A simple counter model")
  (count :type integer :initform 0 :observe t) ; Observe changes to count
  (label :type string :initform "Clicks"))

;; Define a user model
(defmodel user (:docstring "Represents a user")
  (id :type integer)
  (username :type string :initform "anonymous")
  (is-active :type boolean :initform t :observe t)) ; Observe active status

;; --- Composite Model Example (Nesting) ---
;; Define a model for a main view that contains a counter and a button
(defmodel main-view (:docstring "Model for the main application view")
  ;; Child component models are stored directly under keys
  ;; The value associated with :my-counter will be the plist generated by make-counter
  (my-counter :type list :initform (make-counter)) ; Assuming make-counter exists
  ;; Similarly for a button (assuming button-model and init-button exist)
  (submit-button :type list :initform (init-button :submit-btn :label "Submit")))
```

*   This defines the *shape* of the data associated with the keys `'counter`, `'user`, and `'main-view` in the application state.
*   The `main-view` model demonstrates nesting: its state includes the state of child components (`my-counter`, `submit-button`). The actual state for these children (e.g., the counter's plist) is stored under these keys within the main `*app-state*`.
*   `defmodel` generates `make-<model-name>` constructors (e.g., `make-counter`, `make-main-view`), accessors (e.g., `count`, `my-counter`), and potentially `initialize-<model-name>-state` helpers.
*   Slots with `:observe t` will trigger state change messages when updated via `set-state!`.

**2. Define Messages (`defmsg`)**

Specify the messages that drive state changes.

```lisp
(defmsg AppMsg (:docstring "Main application messages")
  ;; --- Component-Specific Messages (Examples) ---
  ;; Counter Example Messages
  IncrementCounter
  DecrementCounter
  (SetCounterLabel :new-label string)
  ;; User Example Messages
  (ActivateUser :user-id integer)
  (DeactivateUser :user-id integer)
  ;; Button Click (Example - could be more specific)
  (ButtonClicked :id t)
  ;; TextInput Change (Example)
  (InputChanged :id t :value string)

  ;; --- Global/System Messages ---
  ;; Focus Management Messages
  (RequestFocus :widget-id t) ; ID can be symbol, string, etc.
  FocusNext
  FocusPrevious
  ;; Theme Message
  (SetTheme :stylesheet t) ; Stylesheet object (type depends on style-lib)
  ;; Observer/Async Messages (Examples)
  (StateChanged :model symbol :slot keyword :value t)
  (AsyncProgressUpdate :task-id symbol :progress t)
  ;; Input Event Messages (Mapped from platform backends)
  (KeyEvent :key symbol :char t :modifiers list)
  (MouseEvent :type keyword :button integer :row integer :col integer :modifiers list)
  (WindowResize :width integer :height integer)
  ;; Internal message for updating focus list
  (UpdateFocusableIds :ids list)

  ;; --- Message Wrapping Example ---
  ;; Message for the main view, wrapping a child message
  (MainViewMsg :child-key symbol :child-msg list))

;; Define a wrapper message for state changes from observers
;; (Alternatively, handle :state-changed directly in the main update)
(defmsg StateChangeMsg (:docstring "Wraps state changes detected by observers")
  (Changed :model symbol :slot keyword :value t))

```

*   This defines message variants like `:increment-counter`, `:set-counter-label`, etc.
*   It generates constructors like `make-increment-counter-app-msg`, `make-set-counter-label-app-msg`.
*   We also define messages (`CounterStateChanged`, `UserStateChanged`, or a generic `StateChangeMsg`) that will be dispatched by our observers.

**3. Initialize `application-state`**

Create the central state container.

```lisp
;; Assume default-theme and other-theme are stylesheet objects created via defstylesheet or load-stylesheet
(defvar *default-theme* ...)
(defvar *other-theme* ...)

;; Assume keymaps are defined using define-keymap
(elmtui.core.keymap:define-keymap *global-keymap*
  ("C-q" '(:quit)))

(defvar *app-state*
  (let ((state (ut.state:make-application-state)))
    ;; Initialize global state
    (ut.state.state::set-state state :current-focus-id nil)
    (ut.state.state::set-state state :focusable-elements '())
    (ut.state.state::set-state state :current-stylesheet *default-theme*)
    (ut.state.state::set-state state :global-keymap *global-keymap*) ; Add keymap
    ;; Component models might contain their own :local-keymap
    state)
  "The global application state instance.")
```

**4. Create Initial Model State**

Use the `make-<model-name>` constructors to create the initial plists.

```lisp
(defvar *initial-counter* (make-counter :count 0 :label "Initial Clicks"))
(defvar *initial-user* (make-user :id 1 :username "Alice"))
```

**5. Add Initial State and Register Observers**

Use the `initialize-<model-name>-state` helpers to populate the `*app-state*` and activate observers. Handle any initial commands returned by the widget `init` functions.

```lisp
;; Assumes *app-sender* is defined and bound appropriately for observer callbacks
;; (defvar *app-sender* #'my-dispatch-function)

;; Initialize state and collect initial commands
(let ((initial-commands nil))
  (multiple-value-bind (model commands) (init-counter-model :count 0 :label "Initial Clicks")
    (initialize-model-state *app-state* 'counter model)
    (setf initial-commands (append commands initial-commands)))

  (multiple-value-bind (model commands) (init-user-model :id 1 :username "Alice")
    (initialize-model-state *app-state* 'user model)
    (setf initial-commands (append commands initial-commands)))

  ;; Process initial commands right after setup
  (process-commands (nreverse initial-commands)))
```

*   This puts `*initial-counter*` into `*app-state*` under the key `'counter`.
*   It registers an observer for the `:count` slot of the `counter` model. When the `:count` value changes later via `set-state!`, the observer will call `*app-sender*` with a message like `(:state-changed :model 'counter :slot :count :value <new-count>)`.
*   Similarly, it registers an observer for the `:is-active` slot of the `user` model.

**6. Define Update Logic (`defupdate`)**

Implement the state transition logic. Use the local `set-state!` macro for all modifications.

```lisp
;; Define the main update function (adjust signature as needed for your app)
;; This example assumes a top-level model 'main-view' exists in the app-state
;; which contains child models like 'my-counter' and 'submit-button'.
(defupdate main-update (app-state msg)
  "Main application update function. Handles global messages and delegates to children."
  ;; First, try to handle focus messages using the dedicated utility.
  ;; elmtui.core.base-focus:handle-base-focus-message expects the app-state, the message,
  ;; and the transactional set-state! function (provided by defupdate's macrolet).
  (if (elmtui.core.base-focus:handle-base-focus-message
       app-state msg (lambda (key value) (set-state! key value)))
      ;; If handle-base-focus-message returns T (message was handled),
      ;; usually no further commands are needed from this level.
      nil
      ;; Else, the message was not a focus message or not handled by the utility,
      ;; so proceed with other application-specific message handling.
      (let ((msg-type (if (listp msg) (first msg) msg))
            (msg-data (when (listp msg) (rest msg)))
            (commands nil)) ; Collect commands from children

        ;; --- Global Message Handling (excluding focus, which is now handled above) ---
        (case msg-type
          ;; --- Theme ---
          (:set-theme
           (let ((new-stylesheet (getf msg-data :stylesheet)))
             (set-state! :current-stylesheet new-stylesheet))
           (return-from main-update nil))

          ;; --- Observer Example ---
          (:state-changed
           (let ((model (getf msg-data :model))
                 (slot (getf msg-data :slot))
                 (value (getf msg-data :value)))
             (log:info "Update loop received state change: Model=~S, Slot=~S, Value=~S" model slot value)
             ;; Potentially return commands based on state changes
             (return-from main-update nil)))

          ;; Note: :update-base-focusable-ids is handled by elmtui.core.base-focus:handle-base-focus-message

          ;; --- Message Delegation Example ---
      (:main-view-msg
       (let* ((child-key (getf msg-data :child-key)) ; e.g., 'my-counter or 'submit-button
              (child-msg (getf msg-data :child-msg))
              (child-model (state-ref app-state child-key))) ; Get the child model plist

         (when child-model
           (multiple-value-bind (updated-child-model child-commands)
               ;; Determine which update function to call based on the child-key or model type
               (case child-key
                 ('my-counter (update-counter child-msg child-model)) ; Assuming update-counter exists
                 ('submit-button (update-button child-msg child-model)) ; Use the button's update
                 (otherwise (progn (log:warn "Unhandled child key in :main-view-msg: ~S" child-key)
                                   (values child-model nil))))

             ;; Update the child model in the main state
             (set-state! child-key updated-child-model)
             ;; Collect commands from the child
             (when child-commands
               (setf commands (append child-commands commands))))))
       ;; Return collected commands after delegation
       (return-from main-update commands))

      ;; --- Direct Handling (If not delegating) ---
      (:increment-counter ; Example if counter wasn't a child component
       (set-state! 'counter (list* :count (1+ (getf (state-ref app-state 'counter) :count))
                                   (state-ref app-state 'counter))))
       (return-from main-update nil))

      (otherwise
       (log:warn "Unhandled message type in main-update: ~S" msg-type)
       (return-from main-update nil)))) ; Return nil for unhandled messages
```

*   `defupdate` wraps the body in `ut.state:with-transaction`.
*   `set-state!` is a local macro within `defupdate` that calls `ut.state:record-change`. It takes the key (e.g., a global key like `:focused-widget-id` or a component model key like `'my-counter`) and the *new complete value* (e.g., the new focused ID, the updated counter plist).
*   The function should return a list of commands (or `nil`).
*   The example shows handling global messages (like focus changes) directly and delegating component-specific messages (wrapped in `:main-view-msg`) to the appropriate child component's update function (e.g., `update-counter`, `update-button`). The results (updated child model and commands) are then integrated back into the main application state.

**7. Create Messages**

Use the generated `make-<variant>-<type>` constructors.

```lisp
(make-increment-counter-app-msg)
(make-set-counter-label-app-msg :new-label "Total")
```

**8. Dispatch Messages**

Send messages to the main update function (e.g., via an event loop and `*app-sender*`).

```lisp
;; Conceptual dispatch (likely part of the main event loop)
(defun process-message (msg)
  (let ((commands (main-update *app-state* msg)))
    ;; TODO: Interpret/execute commands returned by the update function
    ;; This might involve calling elmtui.core.async:interpret-cmd
    (when commands
      (process-commands commands))))

(process-message (make-increment-counter-app-msg))
(process-message (make-focus-next-app-msg))
```

**9. Access State**

Use `state-ref` or the generated model accessors (`<slot-name>`) in view functions or other read-only contexts. The view function retrieves necessary state, including the current stylesheet, to render the UI.

```lisp
(defun view (app-state)
  (let ((focused-id (state-ref app-state :current-focus-id))
        (current-stylesheet (state-ref app-state :current-stylesheet))
        (counter-model (state-ref app-state 'counter)) ; Get the whole model plist
        (user-model (state-ref app-state 'user)))

    ;; 1. Generate the raw UI node tree using widget view functions
    ;;    Pass relevant model parts and focused-id down to component views
    ;;    The component view function will compare its own ID to focused-id
    ;;    (view-counter counter-model (eq focused-id (getf counter-model :id)) ...)
    (let ((raw-view-tree
            ;; ... build UI description using view-widget functions or DSL ...
            ))

      ;; 2. Apply the current stylesheet to the raw tree
      ;;    (Assumes apply-stylesheet-to-tree is available)
      (let ((styled-view-tree (apply-stylesheet-to-tree raw-view-tree current-stylesheet)))

        ;; 3. Pass the styled tree to the layout engine (conceptual)
        ;; (layout-tree styled-view-tree)

        ;; NOTE: Generating the :focusable-widget-ids list happens after the view tree
        ;; is generated. The application runtime (or main loop) should:
        ;; 1. Call a function like `collect-focusable-ids` on the generated `raw-view-tree`.
        ;; 2. Dispatch an `:update-focusable-ids` message with the collected list
        ;;    back into the `main-update` function.
        ;; This ensures the focus order matches the rendered UI.

        ;; Return the final description for rendering (e.g., styled or layout tree)
        styled-view-tree))))
```

**10. Use Undo/Redo**

Call `ut.state:undo-last-transaction` and `ut.state:redo-last-transaction` on the `*app-state*` instance, typically triggered by specific user actions (e.g., Ctrl+Z / Ctrl+Y messages).

```lisp
(defupdate handle-undo (app-state msg)
  (declare (ignore msg))
  (ut.state:undo-last-transaction app-state)
  nil) ; Undo itself doesn't usually generate commands

(defupdate handle-redo (app-state msg)
  (declare (ignore msg))
  (ut.state:redo-last-transaction app-state)
  nil)
```

**11. Handling Component Cleanup ("Destroy")**

The Elm architecture doesn't have explicit "destroy" hooks that run automatically when a component's state is removed. Instead, cleanup (like cancelling timers or async tasks associated with a component) should be handled via **commands** returned by the parent component's `update` function at the moment it decides to remove the child component's state.

```lisp
;; Example: Parent update function removing a child widget
(defupdate parent-update (app-state msg)
  (case (first msg)
    (:remove-child-widget
     (let* ((child-widget-key ...) ; Key for the child model in app-state
            (child-model (state-ref app-state child-widget-key))
            (cleanup-commands nil))

       ;; 1. Generate cleanup commands if needed
       ;;    (e.g., cancel an async task associated with the child)
       (when child-model
         ;; Assuming the child model stores the ID of an async task it started
         (let ((child-task-id (getf child-model :associated-task-id)))
           (when child-task-id
             (push (list :cancel-async child-task-id) cleanup-commands)))) ; Use elmtui.core.async:cancel-cmd structure

       ;; 2. Remove the child state using set-state! (or a helper)
       (set-state! child-widget-key nil) ; Or use a specific 'remove-state!' if available

       ;; 3. Return the cleanup commands
       (nreverse cleanup-commands)))
    ;; other cases...
    ))
```

This ensures that cleanup logic remains within the standard update/command flow.

This workflow provides a robust, transactional, and observable state management system aligned with Elm principles.
