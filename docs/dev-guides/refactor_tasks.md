# Architectural Refactoring Tasks

This document outlines key architectural refactoring tasks identified for improving the Elmtui framework, focusing on API simplification, state management, and developer experience.

## 1. Enhance `defcomponent` Macro (`src/ui/defcomponent.lisp`)

**Goal:** Make component definition more declarative, self-contained, and Elm-like, reducing boilerplate and improving clarity.

**Current State:**
- Defines a CLOS class (primarily for ID and dispatch).
- Generates `init` method to set up initial state plist in global `app-state`.
- Generates no-op `update` and basic `view` methods, requiring user specialization via `defmethod`.
- Can generate accessors for state slots.

**Proposed Enhancements:**
- **Inline Logic:** Allow defining `init`, `update`, and `view` logic directly within the `defcomponent` form.
    - `:init (props) -> (values initial-local-state-plist initial-commands)`
        - `props` are initargs.
        - `initial-local-state-plist` defines values for slots declared in `:state`.
        - Macro handles creating the full state patch for `app-state`.
    - `:update (msg local-state app-state self-id-path) -> (values local-state-changes-plist commands)`
        - `local-state` is the component's current state map.
        - `local-state-changes-plist` is a plist of changed local properties (e.g., `(:prop1 val1)`). Macro converts to global patches.
        - Support declarative message handlers within `:update`, e.g., `(:my-message (msg state app-state id-path) ...)`.
    - `:view (local-state app-state self-id-path) -> view-dsl`
- **Local State Abstraction:**
    - Introduce a `:state` clause to explicitly define local state fields and their types (e.g., `(:state (label "Click Me" :type string))`).
    - Pass the component's `local-state` map directly to the inline `update` and `view` functions.
- **Implicit `id-path` and `app-state`:** Make `self-id-path` and `app-state` consistently available within the inline functions.
- **Simplified State Access:** Encourage use of the passed `local-state` map for reads. For writes, the `update` function's return value handles local changes.
- **Observer/Subscription Integration (Optional):**
    - Consider an `:observes` clause for defining state observers.
    - Consider a `:subscriptions` clause for defining component-local subscriptions.
- **Retain `defmethod` Fallback:** Users should still be able to use `defmethod` for more complex scenarios or to specialize components defined by `defcomponent`.

## 2. Integrate `statelib` Transactions (`src/state/statelib/`)

**Goal:** Ensure all application state mutations are transactional, enabling robust undo/redo and state history.

**Tasks:**
- **Centralize State Mutation:**
    - Refactor `elmtui.state.api:set-path` (and any other primitive state-setting functions used by `elmtui.state.update:apply-patches`) to use `(setf (state-ref app-state path) value)` when operating on an `application-state` object. This ensures changes are logged by `statelib`'s transaction mechanism.
- **Wrap Update Cycle in Transaction:**
    - Modify `elmtui.platform.driver:app-loop`'s main message processing logic to wrap the call to the application's `update-fn` (and subsequent patch application) within `elmtui.statelib.transaction:with-transaction`.
- **Expose Undo/Redo:**
    - Provide a standard way for applications to trigger `undo-last-transaction` and `redo-last-transaction` (e.g., via predefined application messages and commands).

## 3. Refine `defapplication` Macro (`src/app/application.lisp`)

**Goal:** Simplify application definition, particularly the specification of the root UI structure.

**Tasks:**
- **Simplify Root Component Specification:**
    - `:root-viewport-id`: Make optional, defaulting to a standard keyword (e.g., `:elmtui-root-viewport`).
    - `:root-component-dsl`: Explore alternatives:
        - **Convention-based:** Require `:main-component-type` and optional `:main-component-id`. The macro constructs the DSL `(<main-type> :id <main-id>)` as the child of the root viewport.
        - **Root Viewport as App View:** Make the `root-viewport` component more directly configurable with its children via its own initargs. `defapplication` would then focus on initializing this top-level `root-viewport`.
- **Default Initial State:**
    - Confirm `:initial-state-plist` defaults to `nil` or an empty list if not provided (already seems to be the case).
    - Ensure component `init` methods (especially those generated by `defcomponent`) handle default local state sanely if no specific initargs are provided.

## 4. Standardize State Manipulation API

**Goal:** Provide a clear, consistent, and abstracted API for reading and modifying component/application state, hiding patching details where possible.

**Tasks:**
- **Define Helper Functions/Macros (for use within component logic):**
    - **Reading:**
        - `get-local-property (key &optional default-value)`: Accesses current component's state.
        - `get-global-property (path &optional default-value)`: Accesses arbitrary app-state path.
    - **Generating Patches (for traditional `update` methods or `with-update-patch`):**
        - `set-local-property-patch (key value) -> patch`
        - `set-global-property-patch (path value) -> patch`
    - **Direct Transactional Updates (if needed outside patch collection, uses `(setf state-ref)`):**
        - `update-local-property! (app-state self-id-path key value)`
        - `update-global-property! (app-state path value)` (or rely on `elmtui.statelib.state:set-state!`)
- **Integrate with Enhanced `defcomponent`:**
    - The enhanced `defcomponent`'s inline `update` returning local changes (`(:prop val)`) would be the primary way to modify local state.

## 5. Leverage `defmsg` and Message Handling (`src/state/msg.lisp`)

**Goal:** Promote a structured approach to message definition and handling.

**Tasks:**
- **Encourage `defmsg` Usage:** Document as the standard way to define messages.
- **Schema Validation:** Explore runtime validation utilities using `*message-schemas*` if messages can come from untrusted sources (beyond constructor type checks).
- **Declarative Callbacks in `defcomponent`:**
    - As part of enhancing `defcomponent`, allow specifying message handlers directly within the `:update` block, keyed by message variant tags (e.g., `(:my-message (msg local-state ...) ...)`).
- **Unhandled Message Detection:**
    - `defcomponent`-generated `update` methods should provide a configurable behavior for unhandled messages (log, error, or no-op).
    - Consider a global hook for unhandled messages at the application level.
